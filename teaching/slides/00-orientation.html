When does prefix affinity improve session latency—and when does it overload a worker?

Teaching notes · read the reasoning

The layers share an experiment contract rather than becoming three unrelated projects. A tool call pauses a session; during that gap the worker may evict its KV. The next turn may reach a different replica, miss the prefix and repeat prefill. Routing toward the original worker could preserve reuse, but that worker might have a long queue. The capstone measures this tension under controlled conditions. Start with one production engine and two identical replicas. Compare other engines sequentially, keeping total resources comparable.

New depth: GPU execution and Kubernetes reconciliation.

Teaching notes · read the reasoning

Analogies help, but they have limits. A GPU kernel runs asynchronously relative to the Python caller, and memory cannot be released just because a client disconnected if in-flight work can still access it. KV is derived state that can often be recomputed; it is not a durable database record that needs a WAL. Kubernetes continuously reconciles desired and observed state. You will learn these differences explicitly rather than rebuilding familiar HTTP servers or replication mechanisms.

Each boundary answers a different question.

  • Did the load generator send on schedule?
  • Did the request wait for memory or execution?
  • Did the client receive useful content?
  • Were resources released after completion or abort?
Teaching notes · read the reasoning

Use a monotonic clock for client event durations. Record intended arrival and actual dispatch separately so a slow load generator cannot hide offered load. Server queue and execution durations need server instrumentation and clock-domain care; do not subtract arbitrary wall-clock timestamps across machines. On completion, cancellation or failure, the engine must eventually release active references. A stream can have metadata-only events before its first generated content, so “first SSE message” is not necessarily TTFT.

LESSON 00 / 07

Prefill and decode reuse different work.

Prefill

Process a prompt of T tokens.

Compute K/V for every layer and position; predict the next token.

Decode

Process the next input token.

Append its K/V, attend over the cached context, predict again.

prompt tokens → prefill → token 1
(token 1, cached KV) → decode → token 2
(token 2, appended KV) → decode → token 3

Compute-bound prefill / bandwidth-bound decode is a hypothesis to test.

Teaching notes · read the reasoning

Caching removes repeated computation of old keys and values; it does not remove attention over prior context. A decode step can still read a large KV cache. At low batch size, model-weight reads and CPU launch gaps can dominate. Larger batches reuse weights, long contexts increase KV traffic, and tensor parallelism adds communication. Therefore label the bottleneck using a profile and an arithmetic-intensity argument. The first generated token normally comes from the final prompt-position logits, which also matters for a fully cached prompt.

LESSON 00 / 08

Derive dense KV memory, with units.

KV bytes = 2 × L × HKV × D × b × T × B

2Keys and valuesLLayers
HKVKV heads, not query headsDExplicit head dimension
bBytes per elementT, BTokens per sequence, sequence count
2 × 28 × 8 × 128 × 2 = 114,688 bytes/token
114,688 / 1,024 = 112 KiB/token
112 KiB × 32,768 = 3.5 GiB per sequence

Source: huggingface.co — supporting reference

Teaching notes · read the reasoning

This formula counts dense full-attention K/V storage without sharing or page rounding. It excludes weights, activations, attention workspace, graph buffers and allocator overhead. GQA changes KV head count relative to query head count. Use the model’s explicit head_dim when present; Qwen’s head dimension must not be inferred blindly from hidden size divided by query-head count. MLA, hybrid recurrent models and sliding-window attention need different accounting. The model example uses the inspected Qwen3-0.6B-Base dimensions.

LESSON 00 / 09

Try the KV capacity calculator.

Dense full attention, no sharing, no page rounding. Change one input at a time.

This is KV only. It is not a guarantee that a model fits on a GPU.

Teaching notes · read the reasoning

Predict the result before changing a field. Doubling tokens or independent sequences doubles KV storage. Halving bytes per element halves storage, but can change quality and hardware/kernel requirements. A 0.6B model can have several GiB of KV for a long sequence despite relatively small weights. This is why memory management is a core mechanism even when the model seems “tiny.” Prefix sharing changes the number of distinct physical pages; the calculator intentionally assumes no sharing.

LESSON 00 / 10

Pages separate logical order from location.

Page size = four token slots. Logical tokens remain ordered.

Logical page 0
→ physical 7tokens 0–3
Logical page 1
→ physical 2tokens 4–7
Logical page 2
→ physical 9tokens 8–9 + 2 empty
logical_page = token_position // page_size
physical_page = block_table[logical_page]
slot = token_position % page_size

Allocator + block table + KV writes + attention reads must agree.

Source: arxiv.org — supporting reference

Teaching notes · read the reasoning

Paging does not reorder a sequence semantically. It maps logical token positions to physical storage. A gathered PyTorch reference can validate this mapping, but gathering all pages before attention loses some of the intended performance benefit. The fast backend must consume paged metadata directly for a paged-attention integration claim. Initially fix one page size supported by the backend; do not sweep unsupported values. Internal fragmentation is typically the unused tail of allocated pages, while prefix retention and metadata add other memory costs.

LESSON 00 / 11

Prefix reuse has an identity contract.

Block hash

Parent hash + full token block + relevant identity.

Same local tokens under different ancestors must not match.

Radix tree

Compressed token spans with split/match/lock/evict operations.

Page alignment still constrains usable cached storage.

Compare the indexes with the same pool, page size, scheduler and workload.

Why does a branching conversation not prove radix is better?

A chained hash also represents shared prefix ancestry. Hit rate depends on granularity, eviction, capacity and scheduling, not just whether the index is a tree.

Source: docs.vllm.ai — supporting reference

Teaching notes · read the reasoning

Cache identity includes the information that determines the KV values: model/weights, tokens and positions, adapter or other relevant inputs, plus an isolation namespace. Chat templates affect token identity. An arbitrary client-supplied salt is not itself trusted tenant authorization. Both indexes can reuse the same page-aligned prefixes, so compare lookup cost and eviction behavior before attributing differences to the data structure. A full prompt hit may still need computation to produce the final-position logits unless those outputs are cached separately.

LESSON 00 / 12

Continuous batching changes the scheduling unit.

IterationActive requestsChange
1A, BA and B execute one step
2A, BB completes
3A, CC fills released capacity
4CA has completed

Constraints: token budget, available KV pages, request limits and fairness.

Chunked prefill bounds how much new prompt work shares an iteration with decodes.

Source: www.usenix.org — supporting reference

Teaching notes · read the reasoning

Orca motivates scheduling at iteration granularity. This does not imply every engine uses identical batching internals or identical prefill/decode packing. Draw the state changes first. In the implementation distinguish tokens already computed, tokens scheduled in the current step and tokens emitted to the client. Preemption adds a transition back to waiting and may require recomputation; cancellation adds cleanup that must respect in-flight GPU execution. A virtual clock tests these policies without sleeping through thousands of artificial requests.

LESSON 00 / 13

Timing definitions must survive edge cases.

scheduled arrival = 0 ms      dispatch = 20 ms
first token       = 120 ms    last token = 320 ms
finish            = 330 ms    output tokens = 5
Calculate dispatch lag, TTFT, TPOT and E2E.

Dispatch lag = 20 ms. Client TTFT = 100 ms; offered-arrival TTFT = 120 ms. TPOT = (320−120)/(5−1) = 50 ms/token. Client E2E = 310 ms; arrival-to-finish = 330 ms.

For fewer than two output tokens, TPOT is undefined—not zero.

Teaching notes · read the reasoning

This example assumes exact token timestamps, not coalesced chunks. Keep the end-of-stream event separate from the last token so protocol cleanup does not inflate decoding time without being noticed. For SLOs, decide how one-token responses are handled: they can still be judged by TTFT/E2E, but should not be assigned an artificially good TPOT. Avoid silently dropping error or timeout requests from throughput/attainment denominators. The load generator must record dispatch lag so overload of the client is detectable.

LESSON 00 / 14

A streamed chunk is not always a token.

event 1: role / metadata
 event 2: "The answer"        ← may contain multiple tokens
 event 3: " is 42."
 event 4: usage / finish
  • First useful content ≠ first SSE event.
  • Inter-chunk gaps ≠ exact per-token gaps.
  • Retokenized text ≠ an automatic token-timing oracle.

Report what you can observe; instrument the server for finer timing.

Source: docs.nvidia.com — supporting reference

Teaching notes · read the reasoning

SSE transport can split or coalesce model output independently of tokenizer boundaries. Special tokens and incremental tokenization can make counting from chunks misleading. Exact individual token timestamps cannot be reconstructed from one timestamp covering several emitted tokens. Retain raw chunk events and the declared token-count source, report normalized estimates with a limitation if necessary, and cross-check the same metric semantics in AIPerf rather than expecting every similarly named metric to agree.

LESSON 00 / 15

Goodput is useful completed work.

goodput = requests passing every per-request SLO / measured seconds

Example: 100 offered requests in 10 seconds.

  • 90 complete; 10 fail or time out.
  • 70 of the completed requests meet both TTFT and TPOT thresholds.
What are completion throughput, goodput and attainment?

Completion throughput = 9 requests/s. SLO goodput = 7 requests/s. Offered-request SLO attainment = 70%, not 70/90.

Teaching notes · read the reasoning

Two marginal percentile statements do not establish that the same requests meet both requirements. Evaluate each eligible request against the declared conjunction and then aggregate. Also record success/error/timeout/rejection counts. A closed-loop client can hide offered overload by waiting for previous completions, which is why open-loop arrival tests are important for saturation studies. The definition of the observation window and treatment of boundary requests must be fixed before comparisons.

LESSON 00 / 16

Choose the replay question first.

ModePreservesDoes not prove
Fixed-arrival requestsRecorded prompts and arrivalsCausal agent completion time
Dependency-aware transcriptsParent completion + tool delay; fixed next promptLive tool behavior or answer quality
Live agentActual output-driven control flowIdentical load across runs

Fixed output length does not fix output content or branching.

Source: docs.nvidia.com — supporting reference

Teaching notes · read the reasoning

Suppose turn two was recorded at 500 ms, but the new server needs 800 ms to finish turn one. Sending turn two at 500 ms preserves absolute load but violates the original dependency. Waiting until parent completion plus the recorded tool delay gives a meaningful conditional session-timing experiment. Yet using the recorded next prompt means new model output does not alter control flow, so it is still transcript replay. Run live task evaluation separately. Backend-specific minimum-output/ignore-EOS controls can be useful, but max_tokens alone is normally only a cap.

LESSON 00 / 17

Correctness has several layers.

Must be exact

  • Ownership and page conservation
  • Position/mask/cache identity
  • No use-after-free or cross-tenant reuse

Needs a defined oracle

  • Floating-point logits and layer outputs
  • Sampling distributions
  • Quantized model quality

Use teacher-forced tokens to localize numerical divergence.

Source: docs.vllm.ai — supporting reference

Teaching notes · read the reasoning

Small numeric differences can change argmax when two logits are nearly tied; later generated text can then diverge greatly. Compare identical token inputs, intermediate layers and final logits before judging long free-running text. Use FP32 tiny cases first, then backend/dtype tolerances. Do not explain away systematic errors as “floating point.” Sampling correctness concerns distributions; speculative sampling can be correct without reproducing a same-seed ordinary decoding trajectory. Quantization intentionally changes numerical outputs and must pass a separate task-quality gate.

LESSON 00 / 18

The capstone needs a controlled comparison.

1 engine × 3 routers × 2 loads × 2 locality levels × 3 repeats = 36 runs

Primary metric: p95 session completion time.

  • Same model, precision, prompt identity and total GPUs.
  • Round-robin, least-queue and guarded prefix affinity.
  • Separate cold cache, warm cache and cold start.
  • Include a skewed-popularity or stale-metric case.
Teaching notes · read the reasoning

The 36-run plan is a tractable starting design, not a guarantee that three repetitions suffice. Pilot the duration and sample count. If 36 runs each contain five measured minutes, that is three measured node-hours before warmup, preparation, setup and failed runs. Bootstrap whole sessions or runs when observations are dependent. With only 100 observations, p99 rests near a single extreme observation, so avoid precise tail claims from tiny samples. Explain failures and negative results; do not search combinations until a desired speedup appears.

LESSON 00 / 22

Use AI after you can state the design.

  1. Write the state, inputs, outputs and invariant.
  2. Predict a failure and its expected test result.
  3. Let the agent implement or supply the plumbing.
  4. Review the diff and run an independent oracle.
  5. Reconstruct the key mechanism without assistance.

“I can explain why this fails” is stronger evidence than “the generated tests pass.”

Teaching notes · read the reasoning

An AI agent can produce a plausible implementation and tests that share the same mistaken assumption. Separate structural properties and a simple reference oracle from the optimized code. For an allocator, random operation sequences and ownership conservation are stronger than testing one expected happy path. For numerics, compare against a tiny independent reference. For routing, test stale data and overloaded affinity. You do not need to type every line yourself, but you do need to understand the mechanism and describe the assistance accurately.

LESSON 00 / 24

Teach it back before moving on.

1. Why can a small model use more KV memory than weight memory?

KV grows with layers × KV heads × head dimension × sequence length × concurrency. Parameter count alone does not determine it.

2. Why can prefix affinity make a request slower?

Reusing KV can save prefill but add queue delay at a busy worker. Stale locality estimates can add imbalance without delivering reuse.

3. Why are identical greedy strings not the only correctness test?

Numeric drift near an argmax tie can change later text; structural invariants and same-input layer/logit comparisons diagnose the actual mechanism.

4. What does a fixed transcript fail to validate?

Fresh-output-driven tool behavior, answer quality and branching. Evaluate those with a separate live task suite.

Teaching notes · read the reasoning

Answer aloud before revealing. If one is difficult, revisit the corresponding slide and work a smaller example. The next lesson is a short numerical/tensor diagnostic followed by explicit GPU foundations. You should not start a full CUDA kernel implementation merely because this orientation mentions warps and bandwidth. Keep a learning log with a one-week and one-month retrieval question. A finished project is an artifact you can explain under questioning, not a checklist of features you cannot reconstruct.
